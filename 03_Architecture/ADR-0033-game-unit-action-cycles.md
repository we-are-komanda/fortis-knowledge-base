# ADR-0033: Циклы действий и конечные ресурсы игровых юнитов

**Дата:** 2026-11-05

**Статус:** реализовано локально; проверки ниже

**Связанные:** [[ADR-0032-monte-carlo-model-audit]], [[ADR-0029-map-monte-carlo-shared-project]], [[ADR-0018-immutable-project-revisions]]

## Запрос и границы

По запросу пользователя игровые юниты защиты учитывают интервал атак, реакцию, магазин, общий запас зарядов, перезарядку и число разных целей за цикл. Настройки редактируются **для каждого размещения**, с едиными условными значениями по умолчанию. Новые значения — самостоятельные правила игрового баланса; ТТХ из презентации не используются для их калибровки. Движение вражеских юнитов к базе остаётся прежним синтетическим расписанием.

Версии: `mass-motion@7` / `coverage-neutralization@4`. Это изменение игровой механики, поэтому результаты предыдущих версий не обязаны совпадать. В частности, прежняя формула произведения вероятностей по всему маршруту больше не применяется.

## Параметры размещения

Необязательное поле `PlacedDefenseObject.gameSettings` содержит полный объект:

| Поле | Значение по умолчанию | Допустимый диапазон | Смысл |
|---|---:|---:|---|
| `intervalMs` | 5000 | 1000–60000 | Минимальное время между циклами одной единицы |
| `reactionMs` | 2000 | 0–120000 | Задержка от входа цели в непрерывный участок зоны |
| `magazineSize` | 6 | 1–1000 | Вместимость магазина в игровых зарядах |
| `ammunition` | 60 | 0–10000 | Общий конечный запас, включая первый магазин |
| `reloadMs` | 15000 | 0–600000 | Пауза после расходования последнего заряда магазина |
| `maxTargets` | 1 | 1–16 | Максимум разных целей в одном цикле |

Все поля — конечные целые числа. В интерфейсе время показывается в секундах. При отсутствии поля применяются общие значения, без изменения сохранённого старого проекта. Неполный объект, `null`, строки, NaN, Infinity и значения вне диапазона отклоняются. Пустой общий запас запрещает действия; если запас меньше магазина, загружается только доступное число зарядов.

Параметры относятся к **одной** единице: `quantity` одинаковых единиц имеют отдельные магазины, запасы и времена готовности. `maxTargets` означает игровые действия по разным целям в одном цикле, а не модель непрерывного сопровождения или огневых каналов.

## Алгоритм

1. Сохранённый seed и индекс прогона определяют расписание появления и направления врагов. Эти случайные потоки не зависят от настроек защиты.
2. Для каждого маршрута и размещения определяются все интервалы нахождения внутри условного круга/сектора. Сектор более 180° может дать несколько интервалов; смежные интервалы объединяются. Касание без времени внутри не даёт попытки.
3. Цель становится доступна после `вход + reactionMs`. Реакция идёт от входа независимо от занятости единицы. После выхода и повторного входа задержка начинается заново.
4. Циклы всех экземпляров обрабатываются хронологически. При равном времени порядок — лексикографический ID размещения, затем номер экземпляра. Внутри цикла цели выбираются по времени входа, затем ID, без оптимизации приоритета.
5. Готовая единица делает не более `maxTargets` попыток по разным доступным целям, не более имеющихся зарядов магазина. Каждая попытка расходует один заряд и одно случайное число из отдельного потока исходов. Вероятность успеха равна `1 − pPass` из существующей таблицы **игровых** коэффициентов.
6. При успехе враг нейтрализуется в текущем месте и времени; последующие единицы и циклы уже не расходуют на него заряды. `neutralized.by` указывает фактически сработавшее размещение, `units=1` — один сработавший экземпляр. При неудаче цель может участвовать в следующих циклах, пока она внутри зоны.
7. Следующий цикл возможен не ранее `t + intervalMs`. Если магазин опустел, готовность наступает через `max(intervalMs, reloadMs)` после последнего цикла: интервал и перезарядка идут одновременно. Перезарядка не создаёт новые заряды и не выполняется при пустом общем запасе.
8. Попытки разрешены до выхода из зоны и строго до достижения границы базы. При совпадении времени с границей первым считается прорыв. Счётчики, журналы и график активности используют время фактической нейтрализации, поэтому перемотка остаётся обратимой.

Из-за ресурсов и общей очереди монотонность исхода **каждой отдельной цели** при добавлении юнитов не гарантируется. Воспроизводимость гарантируется для одинаковых входных данных, seed, индекса и версии алгоритма; перестановка массива размещений не меняет порядок по их ID.

## UI и сохранение

В панели «Эффективность средств» у каждого размещения раскрывается «Игровые параметры». Валидный ввод применяется при выходе из поля или Enter. Некорректный черновик помечается как неприменённый; Escape отменяет его. Кнопка «Общие игровые значения» удаляет переопределение. Изменение применённых параметров сбрасывает текущий просмотр/результаты и отменяет устаревший пакет; камера и выбор объекта результат не инвалидируют.

Настройки проходят через существующие обновление/дублирование размещения, экспорт/импорт проекта и явное сохранение. Автосохранение и отдельное хранилище сценария не добавлены. Backend сохраняет это frontend-owned расширение в существующем lossless JSON-документе и снимках ревизий; новый endpoint, Go-модель и SQL-миграция не требуются. Backend не интерпретирует эти игровые поля; проверка их значений выполняется во frontend при импорте и на границе расчёта. Это не новый контракт боевых характеристик каталога.

## Ограничения вычисления

Прогон допускает до 1000 участвующих экземпляров и 100000 попыток. Превышение возвращает явную ошибку; частичный результат не публикуется. UI показывает причину и блокирует запуск, пока конфигурация не исправлена. Пакеты по 100/500 прогонов уступают управление каждые 10 прогонов и сохраняют проверку отмены. Если понадобится поднять эти пределы, сначала перенести расчёт в Worker и повторить измерения задержки ввода.

## Проверки

- Frontend: 81 проверка — новая механика и числовые границы, геометрия и повторный вход, фактическое время нейтрализации, ресурсы/количество, сохранение/сброс/дублирование, существующие проектные и save-контракты.
- Backend: тест `TestGameSettingsDocumentRoundTrip` проверяет import → JSONB mapping → reload → export, включая нулевой запас; тесты application/infrastructure проходят без изменения рабочего кода backend.
- Браузерный gate `test/playwright/mc-effectiveness.cjs`: шесть полей, неприменённый ошибочный ввод, сброс значений, отмена устаревшего пакета при изменении запаса, загрузка сохранённых настроек, 2D/3D, desktop/mobile. Сценарий проходит на dev-сервере и production-сборке. API-ответы замоканы, записей нет; ошибок страницы и console нет.
- TypeScript, scoped ESLint, `pnpm build` (отдельный `.next/game-check`) и `go build ./...` проходят. Production browser gate проверяет также отсутствие горизонтального переполнения боковой панели и мобильного экрана. Изменения конфигурации TypeScript, автоматически созданные проверочной сборкой, удалены.
