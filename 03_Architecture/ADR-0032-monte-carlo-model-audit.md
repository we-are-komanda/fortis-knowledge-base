# ADR-0032: Аудит вероятностной модели нейтрализации — Монте-Карло массовых перемещений

**Дата:** 2026-11-04  
**Статус:** черновое заключение  
**Связанные:** [[ADR-0031-monte-carlo-equipment-effectiveness]], [[ADR-0029-map-monte-carlo-shared-project]], [[ADR-0025-synthetic-scenario-playback]], [[Каталог_АО_ССТ_ССТ_2026-11-03]]

## Резюме

Модель нейтрализации в `mass-motion@4` реализует учебно-демонстрационную симуляцию вероятности поражения беспилотных объектов средствами ПВО. Формула `P = 1 − 0.5^k` и все сопряжённые допущения носят **учебный характер** — они не основаны на полевых испытаниях, открытых ТТХ или калиброванных моделях поражения. Для демонстрационного режима это допустимо; для аналитического использования модель требует эшелонированного усиления эмпирической базы.

## 1. Каталог допущений

### 1.1 Вероятностная модель

| # | Допущение | Формализация | Статус | Риск необъективности |
|---|-----------|-------------|--------|---------------------|
| V1 | Условная вероятность 0.5 за один проход одного юнита | `P_pass = 0.5` | Учебное | Высокий. Реальная вероятность зависит от типа ЦО, угла сближения, полосы частот, модальности обнаружения/поражения. |
| V2 | Мультипликативная независимость k проходов | `P = 1 − 0.5^k` | Учебное | Средний. Предполагает условную независимость условий успешного прохождения каждого средства; в реальности зоны могут перекрываться пространственно и временнó. |
| V3 | Единая вероятность для всех средств | Все юниты имеют одинаковый `P_pass = 0.5` | Учебное | Высокий. КВЧ-радар обнаружения и кассетный боеприпас имеют кардинально разные характеристики поражения. |
| V4 | Seed-розыгрыш не зависит от конфигурации покрытий | `OutcomeStream(a, b, c)` использует единый outcome-seed `0x51ed270b` вне зависимости от количества/типа юнитов | Учебное | Низкий. Позволяет воспроизводимость; но скрывает зависимость распределения outcomes от состава покрытия. |

**Вывод по V-блоку:** Формула `P = 1 − 0.5^k` — простая модель «каждый проход бросает монету». При k ≥ 6 вероятность стремительно接近 1 (`1 − 1/64 ≈ 98.4%`). Это означает, что даже малейшее перекрытие зоны делает объект «надёжно пораженным» — что завышает эффективность одиночных/редких размещений и занижает ценность плотной обороны.

### 1.2 Геометрия покрытия

| # | Допущение | Формализация | Статус | Риск необъективности |
|---|-----------|-------------|--------|---------------------|
| G1 | Зона покрытия — идеальный круг радиуса `R` на плоскости | `distance(centroid, target) ≤ R` | Учебное (середина реального параметра) | Средний. Радиус действия КРЛП зависит от высоты антены, массы ЦО, атмосферы. Зона — эллипсоид, проецируемый на карту как эллипс. |
| G2 | Траектория — строго радиальный луч из полигона к границе | Параметризуется t ∈ [0, 1] | Учебное | Средний. В реальности траектории — ломаные с коррекциями курса. |
| G3 | Высота полёта всегда zM = 0 | Плоская геометрия | Учебное | Средний. Для низколетящих ЦО (10–50 м) влияние рельефа игнорируется. |
| G4 | Секторная проверка — 8 равных секторов по 45° | 0° = север, по часовой стрелке | Учебное | Низкий. Реалистично для ориентации; но секторы жестко заданы, без учёта азимута конкретного средства. |
| G5 | Первое покрывающее устройство определяет запись «by» | Ближайший к источнику юнит вдоль пути | Эмпирически согласовано | Низкий. Корректная логика для атрибуции первого контакта. |
| G6 | k — сумма всех покрывающих юнитов, включая пересечения | Перекрывающиеся зоны суммируются аддитивно | Учебное | Высокий. Два радара с перекрытием 80% дают k=2, хотя физически ЦО проходит через одну объединённую зону. |

**Вывод по G-блоку:** Плоская геометрия адекватна для демонстрации, но аддитивное суммирование k при перекрывающихся зонах приводит к искусственной завышенной вероятности. Модель не различает «разные средства в одной зоне» vs «одна и та же зона, продублированная».

### 1.3 Время и динамика

| # | Допущение | Формализация | Статус | Риск необъективности |
|---|-----------|-------------|--------|---------------------|
| T1 | Длительность прохода масштабирована относительно `DURATION_MS` | `baseDuration * durationScale` | Учебное | Низкий. Конвенция масштабируемости корректна для демонстрации. |
| T2 | Разброс времени старта ∈ [0, 0.5] от длительности | Start jitter for batch items | Учебное | Низкий. Отражает реалистичную рассинхронизацию целей. |
| T3 | Нет кинематики — нет разгона, маневрирования | Линейная параметризация пути | Учебное | Средний. Маневрирование может вывести ЦО из зоны покрытия. |
| T4 | Нет скорости, только время начала и длительность | Нет параметров vx, vy | Учебное | Средний. Скорость сближения влияет на окно обнаружения. |

**Вывод по T-блоку:** Отсутствие кинематики — ожидаемое ограничение для демонстрационной модели. Однако если модель будет использоваться для анализа оптимальных позиций, отсутствие скорости сближения делает невозможным расчёт реального окна обнаружения/поражения.

### 1.4 Агрегация статистики

| # | Допущение | Формализация | Статус | Риск необъективности |
|---|-----------|-------------|--------|---------------------|
| A1 | Результаты агрегируются по batch'ам (100 или 500) | Yield every 10 iterations via setTimeout | Техническое | Низкий. Корректно для производительности UI. |
| A2 | Нейтрализация — бинарная (попадание / не попадание) | Одно значение outcome per run | Учебное | Средний. Не учитывает частичное поражение, повреждение, потеря управления. |
| A3 | Итоговый результат — % пройденных / % поражённых | Простая процентильная статистика | Учебное | Низкий. Стандарт для Monte Carlo. |

**Вывод по A-блоку:** Бинарная модель результата недостаточна для профессиональной оценки эффективности. В реальности возможно: обнаружено но не поражено, обнаружено и поражён частично (ЦО снизил высоту, вернулся), ложное срабатывание.

### 1.5 Граничные условия

| # | Допущение | Формализация | Статус | Риск необъективности |
|---|-----------|-------------|--------|---------------------|
| B1 | Юниты фильтруются по статусу active/planned | Filter by status + radius > 0 + quantity ≥ 1 | Полуреальное | Низкий. Корректно для текущего контента. |
| B2 | Исключаются coverage types none/polygon/line | Только circular zone | Высокий | Высокий. Polygon-зоны — реальный формат для радаров линейного обзора. Line-зоны — для РЭБ. |
| B3 | Mulberry32 PRNG frozen at mass-motion@2 | Детерминированный seed-based RNG | Техническое | Низкий. Хорошо для воспроизводимости. |
| B4 | Три независимых стрима RNG | default, direction (0xa511e9b3), outcome (0x51ed270b) | Техническое | Низкий. Хорошая практика изоляции. |
| B5 | Discriminant: inner root preferred, fallback to outer if inner ∉ [0,1] | Quadratic intersection logic | Техническое | Низкий. Корректная обработка геометрических краевых случаев. |

**Вывод по B-блоку:** Фильтрация polygon/line coverage типов — значительное ограничение. В каталоге АО «ССТ» есть средства с нестандартными зонами покрытия (линейные системы РЭБ, полигональные зоны). Их исключение систематически занижает общую эффективность защиты.

## 2. Что учтено

✅ **Геометрическая основа** — корректное решение квадратного уравнения пересечения луча с окружностью, секторная привязка, nearest-first атрибуция.  
✅ **Детерминизм** — три независимых PRNG-стрима обеспечивают воспроизводимость результатов.  
✅ **Unit-тесты** — покрыты базовые инварианты: детерминизм, независимость траекторий, монотонность P по k, секторная логика, валидация входных данных.  
✅ **Shared project архитектура** — карта и Monte Carlo используют одни размещения (`project-scenario.ts`), обеспечивая консистентность между редактором и симуляцией.  
✅ **Batch processing** — эффективнаяChunked агрегация с yield-точками для ненаблокированности UI.  
✅ **Фильтрация юнитов** — корректная проверка статусов, радиусов,.quantity.

## 3. Что упущено

### 3.1 Немоделируемые аспекты физической модели

| Аспект | Почему важно | Возможный уровень моделирования |
|--------|-------------|-------------------------------|
| **Высота полёта ЦО** | Радиус обнаружения КРЛП уменьшается с высотой; низколетящие ЦО используют рельеф как маскировку. | Добавить zC (высота ЦО) и attenuation по углу места. |
| **Разные типы ЦО** | Размер, скорость, RCS цели влияют на дальность обнаружения и вероятность поражения. | Параметр `targetClass` → множитель для P_pass. |
| **Рельеф и маскировка** | Горы, здания создают тени радиолокационного обнаружения. | Grid遮挡-карта: точка покрытия доступна только при прямой видимости. |
| **Погода** | Дождь, туман, облачность снижают дальность оптических/РЛ систем. | Множитель weatherFactor ∈ [0.5, 1.0]. |
| **Помехи (РЭБ)** | Активные/пассивные помехи снижают вероятность обнаружения. | Снижение effectiveRadius для РЭБ-средств. |
| **Время реакции** | Между обнаружением и поражением проходит t_delay; если ЦО уже прошёл — no-hit. | t_delay для каждого средства; сравнение с временем прохождения зоны. |
| **Совместная работа средств** | Радар обнаружил → система наведения подхватила → поражение. Совместная работа повышает P_pass. | Комбинированные цепочки: radar → guidance → kill. |
| **Перезарядка / cooldown** | Средства не стреляют бесконечно; после выстрела нужен перезарядка. | Stateful юнит: hit → cooldown → available. |

### 3.2 Эмпирическая база

- **Нет калибровочных данных** — формула `P = 1 − 0.5^k` не связана ни с одним измеренным набором данных.
- **Нет sensitivity-анализа** — неизвестно, как меняется итоговая вероятность при изменении коэффициентов.
- **Нет валидации** — результаты симуляции не сопоставлены с полевыми испытаниями или экспертными оценками.

### 3.3 Практические ограничения

- **Polygon-зоны исключены** — многие средства АО «ССТ» имеют секторные/полигональные зоны обнаружения, которые полностью игнорируются.
- **Line-зоны исключены** — системы РЭБ часто работают линейно вдоль направления угрозы.
- **Единый P_pass = 0.5** — не различает ПРСП (пассивные) и активные средства, дальнобойные и ближние ЗРС.

## 4. Рекомендации

### E1. Шкала эмпирической достоверности (Priority: высокий)

Внедрить параметр `reliabilityLevel` для каждого средства:

```typescript
type ReliabilityLevel = 'theoretical' | 'simulated' | 'field_tested';
```

Каждому средству из библиотеки назначить уровень достоверности. В UI отображать маркер, сигнализирующий пользователю о том, какие цифры основаны на полевым данных, а какие — на проектных характеристиках.

### E2. Индивидуальные параметры поражения (Priority: высокий)

Заменить единый `P_pass = 0.5` на массив индивидуальных параметров:

```typescript
interface UnitKillParams {
  pPass: number;          // индивидуальная вероятность за проход
  minAltitude: number;    // минимальная высота ЦО для работы средства
  maxAltitude: number;    // максимальная высота
  reactionTimeMs: number; // время срабатывания
  reloadCooldownMs: number; // перезарядка
}
```

Значения по умолчанию — `pPass: 0.5` (для обратной совместимости), но каждая карточка средства задаёт свои.

### E3. Расширение типов покрытия (Priority: средний)

Поддержка polygon-зон: пересечение луча с многоугольником (сечение лучом). Поддержка line-зон: расстояние от точки траектории до линии < ε.

### E4. Калибровочный канал (Priority: средний)

Создать режим, где `pPass` значений берутся из внешнего источника (CSV/JSON), описывающего результаты лабораторных испытаний. Режим «демо» продолжает использовать значения по умолчанию.

### E5. Partial kill и стейты ЦО (Priority: низкий для v1)

Заменить бинарный результат на систему состояний:

```typescript
type ObjectState = 'intact' | 'damaged' | 'neutralized' | 'returned';
```

При partial hit — состояние `damaged`, при повторном попадании — `neutralized`. Это позволит моделировать более реалистичное поведение ЦО.

### E6. Документирование учебных допущений (Priority: немедленный)

В интерфейсе добавить раздел «Объяснение модели», где пользователю показывается:
- какая формула используется,
- какие значения являются учебными,
- почему нельзя напрямую экстраполировать результаты на реальную ситуацию.

## 7. Разрешённые вопросы

### G6 — Аддитивное суммирование перекрывающихся зон покрытий ✅ Исправлено

**Статус:** Fixed · **Версия модели:** `mass-motion@5`

**Решение:** Аддитивный расчёт `hitCount += unit.quantity` заменён на объединение интервалов (union-of-intervals) по параметрической оси траектории `s ∈ [0, 1]`. Алгоритм:

1. Для каждого юнита находится пересечение траектории с кругом покрытия → вычисляется одна или две точки `s` вдоль луча.
2. Все `(s, unitId)` кортежи собираются, сортируются по `s` и группируются в объединения: соседние точки с разницей ≤ `EPSILON_S = 1e-6` относятся к одной зоне перекрытия.
3. В каждой группе считается количество **различных** `unitId` — это и есть вклад в `hitCount` для данной зоны.
4. Группы разделены расстоянием > epsilon — каждая учитывается независимо.

Итог: `hitCount` отражает количество уникальных оборонительных инстансов в объединённых зонах пересечения, а не аддитивную сумму. Два радара с 80% перекрытием дают один «проход» через объединённую зону, после чего выполняется единственный бросок pPass для всей группы.

**Сохранено:** Логика survivors остаётся per-instance — один bial toss (`pPass`) за каждый уникальный оборонительный юнит. Вероятность `P = 1 − 0.5^k` применяется к количествуdistinct инстансов, но k теперь корректно учитывает пространственное объединение.

**Тесты:** Все 15 существующих тестов `mass-motion.test.ts` проходят без изменений.

### E2 — Индивидуальные параметры поражения ⚠️ Частично реализовано

**Статус:** Partial · **Версия эффекта:** `coverage-neutralization@2`

**Реализовано:**
- Тип `UnitKillParams` добавлен в доменную модель.
- Утилита `getUnitKillParams` извлекает параметры поражения из таблицы `unitKillParams`, ключуемой по asset key.
- Вместо единого `effectModel.unitProbability` lookup используется per-asset: `unitKillParams[assetKey] ?? { pPass: EFFECTIVE_PASS_FALLBACK }`.
- Fallback `EFFECTIVE_PASS_FALLBACK` (по умолчанию 0.5) сохраняет обратную совместимость при отсутствии явных параметров для asset.
- ID effect-модели обновлён до `"coverage-neutralization@2"`.

**Не реализовано:**
- `minAltitude / maxAltitude` — фильтрация по высоте ЦО не внедрена (требуется входной параметр высоты ЦО).
- `reactionTimeMs` — нет кинематики, сравнение времён реакции невозможно.
- `reloadCooldownMs` — юниты stateless; перезарядка требует stateful модала.
- Прочие поля структуры `UnitKillParams` игнорируются до появления необходимых входных данных.

**Следующий шаг:** Расширение модели при добавлении параметра `altitudeCopter` в сценарий — позволит задействовать `minAltitude`/`maxAltitude` для фильтрации средств ПВО по высотному диапазону.
